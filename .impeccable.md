# Cadence Design Direction

## Design Context

### Users

Cadence is a macOS menu bar utility for engineering and product teams running short, live standups. People glance at it while speaking, so they need to understand the board, transcript, proposed actions, recording state, and any recovery step immediately.

### Brand Personality

Calm, capable, and precise. Cadence should feel trustworthy and fast, with enough warmth to be approachable but no decorative noise.

### Aesthetic Direction

- Native macOS utility, not a web dashboard inside a popover.
- Light, restrained surfaces with strong typography, rigorous alignment, and minimal chrome.
- System typography and SF Symbols. Blue is the primary action accent; other colors communicate status only.
- Dense but readable information, using whitespace and dividers before borders, shadows, or additional cards.
- Preserve the current interface as the visual reference unless the user explicitly asks for a broader redesign.
- Avoid gradients, glass effects, ornamental icons, pill clusters, excessive rounding, and dashboard-card mosaics.

### Design Principles

1. **Keep the working state visible.** The board, recording controls, and current status must remain easy to find. Do not hide primary content behind an unnecessary scroll container or arbitrary height cap; adapt only when the available screen bounds require it.
2. **Use compact, consistent rhythm.** Start from a 4-point spacing system. Keep related labels and controls close, separate sections clearly, and avoid padding that makes a menu utility feel like a full-size window.
3. **Prefer native behavior.** Use SwiftUI and AppKit conventions, platform controls, system typography, and SF Symbols. Device selection, keyboard focus, menus, and error recovery should behave like macOS.
4. **Give each region one job.** Maintain a clear sequence: identity, board, speaker setup or live transcript, recent actions, recovery state, and footer controls. Avoid competing calls to action.
5. **Make failures actionable.** State the problem in plain language and place the relevant recovery action beside it. Keep banners to one line when practical, truncate noncritical device names, and never let copy obscure the action.
6. **Use utility copy.** Labels should orient, report status, or prompt an action. Keep supporting text to one short sentence and remove repeated or promotional language.
7. **Design accessibly.** Do not rely on color alone for state. Preserve readable contrast and type sizes, adequate control targets, keyboard operation, and useful accessibility labels.

## Agent Workflow

Before changing the interface:

1. Read this file, `macos/Sources/Cadence/Theme.swift`, and the affected view.
2. Use the latest user-provided screenshot as a visual reference when one exists.
3. Reuse existing tokens and components. Add a new color, radius, font treatment, or layout rule only when the requested outcome cannot be expressed with the current system.
4. Keep the change scoped. A local adjustment is not permission to restyle neighboring surfaces.

After changing the interface:

1. Run the Swift tests and a release build through the repository's `just` recipes.
2. When app launch is available, relaunch Cadence and inspect the rendered result.
3. Check that primary controls and board content are visible, text does not wrap unexpectedly, long device names truncate safely, banners retain their action, and no unintended scrollbar or clipping appears.
4. Compare the result with the supplied reference and the design principles above, then iterate if needed.
